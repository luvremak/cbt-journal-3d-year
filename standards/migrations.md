# Міграції без простою

Під час деплою на стейдж нова версія спершу застосовує міграції, а стара ще кілька хвилин обслуговує запити (Render перемикає трафік лише після того, як новий екземпляр відповів 200 на `/health`). Тому **кожна міграція мусить бути сумісною з версією, яка зараз працює**.

## Критерії

1. **Стара версія працює на новій схемі.** Це перевіряє CI-джоб `compat`: попередня версія з `main` запускається, нова застосовує свої міграції, і smoke-сценарій проганяється проти _старого_ сервера. Якщо сценарій падає, міграцію не можна мержити.
2. **Expand → contract.** Несумісну зміну розбивають на кроки в різних релізах:

   | Потрібно                   | Реліз N (expand)                                        | Реліз N+1                        | Реліз N+2 (contract)                                    |
   | -------------------------- | ------------------------------------------------------- | -------------------------------- | ------------------------------------------------------- |
   | Перейменувати колонку      | додати нову колонку; код пише в обидві, читає зі старої | backfill; код читає з нової      | видалити стару колонку                                  |
   | Нова обов'язкова колонка   | додати `NULL`-колонку або з `DEFAULT`                   | backfill; код завжди її заповнює | `SET NOT NULL` (через `CHECK … NOT VALID` + `VALIDATE`) |
   | Видалити колонку / таблицю | код перестає її використовувати                         | —                                | `DROP`                                                  |
   | Індекс на великій таблиці  | `CREATE INDEX CONCURRENTLY` (файл без транзакції)       | —                                | —                                                       |

3. **Заборонено в одному кроці:** `RENAME`/`DROP` того, що читає поточна версія; `ADD COLUMN … NOT NULL` без `DEFAULT`; зміна типу колонки; `CREATE INDEX` без `CONCURRENTLY` на таблиці з живими даними.
4. **Не блокувати трафік.** Кожна міграція виконується з `lock_timeout = 5s`. Якщо таблицю зайнято, міграція падає (і деплой теж), а не зупиняє всі запити до неї.
5. **Застосовані міграції не редагуються.** Раннер зберігає контрольну суму й відмовляється працювати, якщо файл змінився. Виправлення — нова міграція.
6. **Один мігратор за раз.** Два екземпляри, що стартують одночасно, серіалізуються advisory lock-ом. Чекати на нього треба в застосунку (`pg_try_advisory_lock` + пауза), а не в SQL (`pg_advisory_lock`). Сесія, що «висить» у SQL, — відкрита транзакція, і `CREATE INDEX CONCURRENTLY` іншого мігратора чекатиме на неї вічно: це дедлок, який знайшов тест (audit/task-5.md).
7. **Відкат — новою міграцією вперед** (roll forward). Невдала міграція відкочується своєю транзакцією і зупиняє деплой; стара версія при цьому працює далі на незміненій схемі.

## Механіка

- Файли `migrations/NNN_опис.sql`, застосовуються за алфавітом командою `npm run db:migrate` (на стейджі — у `npm run start:prod` перед запуском сервера).
- Перший рядок `-- migrate:no-transaction` вимикає транзакцію (потрібно для `CREATE INDEX CONCURRENTLY`). У такому файлі має бути одна ідемпотентна інструкція, наприклад `CREATE INDEX CONCURRENTLY IF NOT EXISTS`.
- Застосовані міграції видно в `GET /version` (поле `migration`).
