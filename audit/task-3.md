# Аудит Завдання 3 — топ-3

Дата: 2026-11-09. Аудитор: Claude (AI). Предмет: тести, мутаційне тестування і те, що вони виявили в коді та spec.

Підсумок: 305 тестів (unit, інтеграційні, E2E на memory і PostgreSQL), mutation score Stryker **100 %** (541 мутант), SQL-мутанти **13/13**, покриття рядків 93 %. Знахідки нижче — це те, що тести й аудит виявили поза цими цифрами. Правило курсу: виправлення через зміну spec / критеріїв.

## 1. Список клієнтів сортується не за українською абеткою

- **Що не так:** spec визначає порядок лише для записів і нотаток. Для `GET /therapist/clients` код сортує за ім'ям побайтово (`COLLATE "C"`), щоб пам'ять і PostgreSQL збігалися. У Unicode літери `Є`, `І`, `Ї` стоять перед `А`.
- **Сценарій:** у терапевта клієнти Андрій, Богдан, Євген, Ірина. API повертає порядок «Євген, Ірина, Андрій, Богдан». Перевірено на PostgreSQL 16 і в Node.js.
- **Чому в топі:** це помилка, яку побачить кожен користувач. Spec цей порядок не визначає, тож зараз вона «легальна».
- **Виправлення в spec:** розділ 4, «Сортування списків» — дописати порядок для списку клієнтів. Варіанти: за ім'ям українською абеткою (PostgreSQL `COLLATE "uk-x-icu"`, у коді `localeCompare(..., 'uk')`; обидва доступні) або, наприклад, за датою прикріплення.
- **Статус:** чекає рішення в spec.

## 2. Тести з БД могли мовчки пропускатися

- **Що не так:** спершу тести з PostgreSQL вмикалися лише за наявності `TEST_DATABASE_URL`. Без змінної `npm test` був зелений, хоча інтеграційні тести та E2E на PostgreSQL не запускались.
- **Сценарій:** у CI (Завдання 4) забули змінну оточення або БД не піднялась, а пайплайн зелений. Регресію в SQL (наприклад, втрачений `FOR SHARE`) ніхто не побачить.
- **Виправлення критеріїв:** `standards/testing.md`, критерій 2: тести з БД обов'язкові, а без доступної БД прогін **падає**. Без БД можна запускати лише явно (`npm run test:nodb`). Код приведено до критерію: `vitest.config.ts` вимагає БД і за замовчуванням бере базу з docker-compose; `vitest.nodb.config.ts` — для unit-тестів і Stryker.
- **Перевірка:** коли PostgreSQL зупинений, `npm test` падає з повідомленням «PostgreSQL is not reachable … `make db-up`».
- **Статус:** виправлено.

## 3. Найважливіша логіка — в SQL, а Stryker її не мутує

- **Що не так:** Stryker міняє JavaScript, але не умови всередині SQL-рядків. Атомарність нотаток (`FOR SHARE`), приховування видалених (`deleted_at IS NULL`), «лише свої» (`therapist_id = $2`) і сортування живуть саме там. 100 % від Stryker про них нічого не каже.
- **Сценарій:** хтось прибирає `AND therapist_id = $2` з запиту нотаток. Stryker нічого не помітить, бо PostgreSQL-репозиторії він навіть не мутує.
- **Виправлення критеріїв:** `standards/testing.md`, критерій 5: кожна бізнес-умова SQL записана в `test/sql-mutants.tsv`, і `make mutation-sql` має вбивати 100 %. Скрипт `scripts/sql-mutation.sh` по черзі підміняє умови й запускає інтеграційні та E2E тести.
- **Перевірка:** 13/13 SQL-мутантів убито. Окремо перевірено, що без `FOR SHARE` падають обидва тести атомарності.
- **Статус:** виправлено.

## Інше (не в топі)

- `src/db/migrate.ts` (39 %) і `src/db/seed.ts` (67 %): не покриті CLI-обгортки і відкат зламаної міграції. Варто покрити в Завданні 4 разом з «міграціями без простою».
- Інкрементальний режим Stryker перевикористав застарілі результати, і мутанти, вбиті новими тестами, показувались як «вижили». Його вимкнено; повний прогін триває ~3 хв.
- Під час написання тестів знайдено й спрощено зайві гілки коду, які давали еквівалентних мутантів: подвійна перевірка видалення в `NoteService`, подвійний кеш у DI, зайві умови в схемі `rational_response` і в обробнику помилок. Поведінка не змінилась, і це підтверджують ті самі E2E-сценарії.
