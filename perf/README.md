# Перформанс

## Як міряємо

```bash
make db-up && make perf          # підготовка даних + навантаження + звіт (reports/index.html)
```

- **Дані** (`perf/prepare.ts`): окрема база `cbt_perf`. 20 терапевтів × 25 клієнтів по 140 записів, «важкий» клієнт Максим — 2000 записів за рік (кожен 10-й видалений), клієнт для сценарію DELETE — 30 тис. записів; нотатки до кожного 10-го запису. Разом ~102 тис. записів і ~10 тис. нотаток. Записи вставляються в порядку часу, впереміш між клієнтами, як у живій системі. Перша версія генератора вставляла записи клієнта підряд, і це робило запити «за клієнтом» нереально дешевими.
- **Навантаження** (`perf/load.ts`): зібраний застосунок (`dist`) окремим процесом, `LOG_LEVEL=info`, як на стейджі. autocannon, 20 одночасних з'єднань. Кожен сценарій: прогрів 2 с, потім 3 прогони по 8 с, у звіт іде медіана.
- **Середовище:** 2 vCPU на застосунок, PostgreSQL і генератор навантаження разом. Окремий прогін тут шумить на ±15 %, тому висновки робимо лише з медіан і порівнюємо «до» і «після» на тій самій машині та тих самих даних.
- **«До»:** збірка з `main` на схемі з міграцій `main` (`perf/prepare.ts --migrations <каталог>`, `perf/load.ts --app <каталог>`).

## Сценарії

Spec §7 вимагає «p99 **кожного** ендпоінта ≤ 50 мс», тож сценарій є для кожного з 12 ендпоінтів.

| Сценарій                              | Запит                                                                                                                                         |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Службове: /health, /version           | `GET /health`, `GET /version`                                                                                                                 |
| Клієнт: свої записи, 1-ша сторінка    | `GET /client/entries`                                                                                                                         |
| Клієнт: свої записи, глибока сторінка | `GET /client/entries?limit=50&offset=1500`                                                                                                    |
| Клієнт: один запис                    | `GET /client/entries/:id`                                                                                                                     |
| Клієнт: свій терапевт                 | `GET /client/therapist`                                                                                                                       |
| Клієнт: новий запис                   | `POST /client/entries`                                                                                                                        |
| Клієнт: видалення запису              | `DELETE /client/entries/:id` — кожен запит видаляє інший запис з 30 тис. підготовлених; міряється кількістю запитів (1000 прогрів + 3 × 8000) |
| Терапевт: список клієнтів             | `GET /therapist/clients`                                                                                                                      |
| Терапевт: записи клієнта              | `GET /therapist/clients/:id/entries`                                                                                                          |
| Терапевт: нотатки до запису           | `GET /therapist/entries/:id/notes`                                                                                                            |
| Терапевт: нова нотатка                | `POST /therapist/entries/:id/notes`                                                                                                           |

Запитів за секунду = запити прогону / його тривалість за годинником. (autocannon округлює тривалість до секунд: 8000 DELETE за 4,6 с показував як «4 с», тобто 2000 rps.)

### Кеш користувачів

`CachingUserRepository` — декоратор над `UserRepository`, підключений через DI лише для PostgreSQL. Кешує `findById` у пам'яті процесу на `USER_CACHE_TTL_MS` (60 с), до `USER_CACHE_MAX` записів (10 000), найстаріший витісняється першим. Чому це безпечно: користувачі з'являються лише через seed, і API їх не змінює (spec §7). Відсутніх користувачів не кешуємо, тож новий seed видно одразу. `USER_CACHE_TTL_MS=0` вимикає кеш.

### Глибокі сторінки

Spec §4 вимагає `limit`/`offset`, тому keyset-пагінація не підходить. Натомість з `offset ≥ 200` id сторінки шукаються лише в покривному індексі (`index-only scan`, без звернень до таблиці), а повні рядки дочитуються тільки для `limit` штук. Індекси `entries_client_active_page_idx` (частковий, `deleted_at IS NULL`) і `entries_client_page_idx` створюються міграціями `CREATE INDEX CONCURRENTLY`, щоб не блокувати таблицю під час деплою.

## Контроль у CI

Джоб `perf` проганяє ті самі 12 сценаріїв (3 × 5 с) і падає, якщо p99 будь-якого з них перевищує **50 мс** або є помилки. Регресія на кшталт втраченого індексу чи deferred join (глибока сторінка без них мала p99 74 мс) зупинить мерж.
